# Day 4 — Event source and alert rule reference

This reference records the five log sources and the event rules used by the home-server Python monitor.

## Inputs

| Label | Path | Events of interest |
|---|---|---|
| FAIL2BAN | `/var/log/fail2ban.log` | `Ban `, `Found `, `Failed` |
| AUDIT | `/var/log/audit/audit.log` | audit records generated by configured audit rules |
| LAN | `~/lan-monitor/changes.log` | new, added, unknown, and changed device records |
| SSH | `/var/log/auth.log` | failed password, failed public-key, invalid user, authentication failure |
| FIREWALL/UFW | `/var/log/kern.log` | `UFW BLOCK` |

The monitor polls these files every two seconds and begins at the current end of each file, so old entries are not replayed at startup.

## Severity and correlation

- Fail2ban ban: MEDIUM; HIGH when at least three ban events occur in a 600-second window.
- SSH authentication failure: MEDIUM; HIGH when at least three matching failures occur in a 600-second window.
- UFW block: MEDIUM; HIGH when at least ten block events occur in a 60-second window.
- Audit event: MEDIUM.
- LAN new/added/unknown/changed event: MEDIUM.
- Other LAN change-log event: INFO.

Correlation uses in-memory time-window counters. It is not durable across a monitor restart.

## Interpretation

Severity is a triage signal, not proof of compromise. A failed SSH login or firewall block can be caused by legitimate troubleshooting. Correlate the timestamp, source, target, and surrounding system activity before deciding whether an incident occurred.

## Privacy

Do not paste raw log records into public issues or commits. Redact account names, IP addresses, MAC addresses, hostnames, and tokens before sharing diagnostic output.
